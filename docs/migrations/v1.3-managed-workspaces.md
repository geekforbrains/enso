# Migrating to v1.3 managed workspaces

Enso v1.3 makes workspace locations name-derived. A workspace named `client-a`
always lives at `~/.enso/workspaces/client-a`; `workspaces.<name>.path`, external
workspace roots, workspace symlinks, and workspace-root Git repositories are no
longer supported. Enso does not move existing content automatically because only
the operator can resolve collisions and decide which files remain authoritative.

Keep the upgraded service stopped until `enso config check` succeeds.

## 1. Stop Enso and make recoverable backups

Stop all Enso service and foreground processes before editing configuration or
moving files:

```bash
enso service stop
cp -a ~/.enso ~/.enso-backup-before-v1.3
```

Back up every configured external workspace separately. Keep the backups on the
same filesystem when possible so ownership, permissions, symlinks, and hidden
files are retained. Treat `config.json` and its backups as private because they
may contain transport credentials.

## 2. Choose valid names and inspect collisions

Workspace names must be at most 64 characters of lowercase letters and numbers,
separated only by single hyphens, such as `default`, `client-2`, or `2fa`.
Renaming `Client_A` to `client-a` changes every transport route and job that
references it.

For each workspace, inspect both its old root and its required destination before
copying anything:

```bash
find /old/workspace -mindepth 1 -maxdepth 1 -print
find ~/.enso/workspaces/client-a -mindepth 1 -maxdepth 1 -print
```

If the destination already contains content, stop and reconcile it file by file.
Do not let `cp`, `mv`, or `rsync` silently replace `AGENTS.md`, `CLAUDE.md`,
`knowledge/`, `skills/`, `.agents/`, or `.claude/`. Prefer the established
authoritative copy, merge instructions intentionally, and rename conflicting
files until their ownership is clear.

## 3. Move or copy the complete workspace

Create the physical parent and destination directories as the user who runs
Enso. The destination and `~/.enso/workspaces` must be real directories, not
symlinks:

```bash
mkdir -p ~/.enso/workspaces/client-a
cp -a /old/workspace/. ~/.enso/workspaces/client-a/
```

The `/.` form is intentional: it includes dotfiles. A same-filesystem `mv` is
also acceptable when the destination is absent, but copying is easier to roll
back. Preserve file ownership and modes; then confirm the Enso service user owns
the resulting tree and can read its durable content and write `knowledge/`,
`drafts/`, and `uploads/`. Do not loosen permissions broadly to make validation
pass.

A `.git` directory, file, or symlink directly inside the workspace is invalid
because `~/.enso` now owns the local history boundary. Move that `.git` entry
into the backup rather than deleting it until migration is verified. Repositories
deeper inside the workspace may remain. Also replace a symlinked workspace root
with a physical copied directory; Enso will not follow it as a compatibility
shortcut.

## 4. Update `config.json`

Remove `path` from every workspace entry. Keep only `policy` and optional
`concurrency`:

```jsonc
{
  "workspaces": {
    "default": {
      "policy": "admin",
      "concurrency": 1
    },
    "client-a": {
      "policy": "client-readonly",
      "concurrency": 2
    }
  }
}
```

Update every Telegram binding, Slack route, and `JOB.md` workspace reference if
a workspace was renamed. Do not add an alternative root or symlink path; there
is no legacy-path fallback.

## 5. Handle setup state, user content, and structural repair deliberately

An existing configuration with no `setup` field is a pre-feature installation.
Leave that field absent. Enso does not interpret it as an interrupted fresh
setup and will not seed a new global prompt, global skills, starter docs, or
workspace content into that installation. Do not add a `setup` block or set
`setup.completed_at` to `null` to trigger seeding; that value is written by Enso
before a genuinely fresh setup seeds content and is retained only while that
initial transaction is incomplete. Fabricating it on an older installation can
turn existing user content into seed collisions rather than perform a migration.

A genuinely fresh setup seeds the global prompt and skills; the starter references
`docs/enso/content_model.md`, `docs/enso/layout.md`, and `docs/operator.md`; and the
default workspace prompt and knowledge index. It then records the complete tree in
one initial local Git snapshot before writing a timezone-bearing completion
timestamp. A completed marker, absent pre-feature marker, structural repair,
startup, and upgrades never run that seed path.

Adopt any of this content into an upgraded installation manually and deliberately.
First review the versioned sources under `src/enso/prompts/`, `src/enso/skills/`, and
`src/enso/starter_docs/` (or inspect them in a separate fresh temporary install).
Compare them with the existing authoritative files, then copy or merge only the
specific prompt guidance, skills, and starter references you want into
non-conflicting destinations. Run `enso doc list` afterward to confirm that adopted
doc names and descriptions are discoverable. Do not expect setup repair to copy
them and do not manufacture a fresh-setup marker. Once adopted, every copy is
user-owned and Enso will not upgrade, replace, or resurrect it after deletion.

Each workspace must ultimately have this structural contract:

```text
~/.enso/workspaces/<name>/
├── AGENTS.md
├── CLAUDE.md -> AGENTS.md
├── skills/
├── .agents/skills -> ../skills
├── .claude/skills -> ../skills
├── knowledge/
├── drafts/
└── uploads/
```

Global skills use the same pattern at `~/.enso/skills/`,
`~/.enso/.agents/skills -> ../skills`, and
`~/.enso/.claude/skills -> ../skills`. Resolve any skill directory name found at
both global and workspace scope; the duplicate makes that workspace invalid.

Older releases may have left zero-byte deletion markers under
`~/.enso/skills/.deleted/`. Current Enso gives that directory no special meaning and
does not migrate or detect it. Inspect it, then move the complete directory into the
backup before creating local content snapshots:

```bash
if [ -e ~/.enso/skills/.deleted ] || [ -L ~/.enso/skills/.deleted ]; then
  if [ -e ~/.enso-backup-before-v1.3/legacy-skill-deletion-markers ] || \
     [ -L ~/.enso-backup-before-v1.3/legacy-skill-deletion-markers ]; then
    exit 1
  fi
  mv ~/.enso/skills/.deleted ~/.enso-backup-before-v1.3/legacy-skill-deletion-markers
fi
```

Stop if the backup destination already exists and reconcile it rather than replacing
either copy. Do not translate the markers into another runtime mechanism; installed
skills are now user-owned, and an absent skill remains absent without a tombstone.

After placing the user-owned files and workspace roots, run explicit setup while
the service remains stopped:

```bash
enso setup
```

For an existing pre-feature or completed installation this is conservative
structural repair: it creates missing managed directories and missing exact links,
recognizes correct links, and reports unexpected files or unknown symlink targets
without replacing them. It does not recreate `AGENTS.md`, `knowledge/README.md`,
skills, or any starter doc. Review every warning; a second run after correcting
conflicts is a no-op.

## 6. Validate while stopped

Claude and Codex now use native ancestor discovery instead of Enso passing a duplicate
shared prompt. Remove top-level `developer_instructions` from every restricted Codex
`config.toml`; put that guidance in the appropriate root or workspace `AGENTS.md`.
Files left by older releases under `~/.enso/runtime/instructions/` are not read by the
new launch path. Move that directory into the migration backup if you want to retain it,
then leave runtime state for Enso to recreate as needed.

Run the read-only validator and fix every reported problem:

```bash
enso config check
```

Confirm that each reported workspace path is exactly
`~/.enso/workspaces/<name>`, every workspace is a physical directory without a
root `.git` entry, `~/.enso` is the exact non-corrupt Git worktree root, policies
resolve as intended, and root/workspace skill names do not collide. Confirm the exact
link targets with `readlink` if needed; do not replace an unknown file merely to silence
a warning. The validator is read-only and will never repair the remaining problem for
you. Every job preflight and actual provider spawn repeats the discovery check, so a
layout that changes after this command still fails closed.

## 7. Restart, verify, then retire the old roots

Reinstall the service definition if the old one embeds obsolete paths, then
restart and inspect status and logs:

```bash
enso service install
enso service restart
enso service status
enso service logs
```

Verify at least one turn for each configured transport, workspace, and enabled provider,
then run a representative job manually. For Claude and Codex, confirm one global and one
workspace instruction layer and both skill scopes are visible without a duplicate shared
prompt; for Grok and Agy, confirm the explicit shared layer appears once. Also confirm
provider selection, knowledge access, uploads, drafts, and replies use the managed
workspace. Keep the old workspace directories and all backups until those checks pass.
Only then remove or archive the old roots; never delete the sole backup as part of the
migration.
